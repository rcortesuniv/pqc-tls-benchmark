# Results dashboard

Generate a self-contained browser dashboard for a completed run:

```bash
analysis/dashboard.py results/pqc-tls-pilot-20260727T100719Z
```

The command refreshes the derived analysis files and writes
`analysis/dashboard.html` inside that result directory. It does not alter raw
JSONL observations, the frozen schedule or integrity evidence.

In Codespaces, the development container starts a dashboard server on port
8000. It selects the newest available result directory by default and
regenerates the dashboard whenever `/dashboard.html` is requested. Rebuild the
container once after pulling the repository change, then use the automatically
forwarded port.

To run the same server manually outside Codespaces:

```bash
python3 analysis/dashboard_server.py --bind 0.0.0.0 --port 8000
```

Open `/dashboard.html` through the forwarded port. Use the group, RTT and loss
filters to examine condition summaries. The dashboard aggregates batch-cell
medians for display; its contrast table retains the batch-aware intervals and
Holm-adjusted values generated by `summarise.py`.

When more than one result directory under `results/` has generated analysis
output, a **Run** selector appears next to the validation badge listing every
servable run, newest first. Choosing one loads `/dashboard.html?run=<name>`;
the same URL can be shared or bookmarked directly. Requesting an unknown or
no-longer-servable run name falls back to the newest available run and shows
a notice explaining why.

## Findings

`summarise.py` also writes `analysis/findings.json`: a short, auto-generated
prose summary computed once per run from that run's own already-computed
outputs (nothing is re-analysed). The dashboard renders it as a "Findings for
this run" section below the reading guide, in two parts:

- A **plain-language paragraph** (`plain_language_summary`) written for a
  general reader, tied to the project's actual objective — whether adding
  post-quantum key exchange to TLS 1.3 costs anything worth worrying about
  compared with classical key exchange. No statistical jargon; its conclusion
  is derived from, not independent of, the technical findings below it, and
  is phrased conditionally (it does not always report a favourable outcome —
  a large overhead or a group-specific loss effect changes the wording).
- Technical bullets covering validation status, the pre-specified primary
  contrast (correctly framed with no multiplicity adjustment — distinct from
  the Holm-adjusted exploratory contrasts), a multiple-comparisons power note
  tied to the configured batch count, the hybrid-vs-classical overhead range,
  and tail behaviour under the harshest tested loss condition.

Both are a starting point for interpretation, not a substitute for reviewing
the full contrast table — and if `analysis.primary_comparison` is missing
from the experiment config, the primary-contrast finding (and the plain-
language paragraph) say so explicitly instead of silently omitting it.
